### 公平性规则

- **各用各的自然用法**：同步库用线程池驱动，异步库用 asyncio 驱动。不假装某一种模型普遍更优。
- **并发 = 连接数**：每个工作线程持有自己的连接池会话，并发 C 即 C 条池化连接，各库一致。
- **预热 + 多次取中位**：先跑 1 s 丢弃，再重复 3 次每次 4 s，取中位数那一次作为该单元结果。
- **同时报告吞吐与延迟分位**：只报 req/s 会掩盖尾部延迟，只报延迟分位会掩盖吞吐。
- **CPU-ms/请求**：用进程 CPU 时间除以请求数，衡量每请求的真实处理开销。
- **同预设立场**：curl_cffi 与 nb-curl 都用两者共有的最新 Chrome 预设（性能对比用 chrome150），避免用不同版本的模拟目标制造差异。
- **证书**：服务端是自签证书，全部以 verify=False 连接，各库相同。
- **为每个库找对它自己的正确用法。**requests_go 初版被配成手工挂载 `TLSAdapter`，这会让会话 id 与 TLS 配置失联、连接复用失效，每个请求都重做一次 TLS 握手 —— HTTPS 场景只有 33 req/s。改用官方预设（`s.tls_config = TLS_CHROME_LATEST`）后，同一场景是 2183 req/s。**配置错误的代价远大于库之间的真实差距**，所以每个库都按其官方推荐方式配置、复核过才计入结果。

### 检查中发现的问题

下面几条不是「谁的分数高」，而是这次实测过程中直接撞到的问题，都附了可复现的观测方式。

> **requests_go：开启浏览器 TLS 预设后，证书校验失效**<br>同一个自签证书服务端：用 requests_go 的普通适配器请求并 `verify=True` 会正确报 `SSLError`；但一旦挂上 `TLS_CHROME_LATEST` 预设，`verify=True` 就不再拦截，请求直接成功。<br>对做数据采集的脚本来说这是**安全相关的行为差异**：以为开了校验，实际在指纹伪装路径上没有任何校验。用它抓取 HTTPS 时请自行确认这一点。

> **httpx 异步客户端在本机高并发下严重退化（平台特性，不是脚本问题）**<br>httpx 的异步客户端在并发 64 以上出现数量级退化：并发 h1_c64 时只有 63 req/s，p50 达到 540 ms。这些单元与其它库用完全相同的驱动方式（asyncio 协程池）测量。单独复测也复现了同样的坍塌（并发 64 两次独立测量分别约 159 与 63 req/s，说明该区间本身抖动很大，但「明显低于同代其它库」的结论是稳的）。<br>原因指向 Windows 默认的 Proactor 事件循环；同一份代码在 Linux 上通常不会这么差。所以这条更适合读作**「在这类 Windows 客户端机器上」的结论**，而不是 httpx 的普遍性能画像。

### 关键差异说明

- **TLS/HTTP2 协商**：默认即走 HTTP/2 的：httpx(h2)、curl_cffi、requests_go、nb_curl；只走 HTTP/1.1 的：requests、aiohttp、httpx。httpx 需显式开启 http2，本报告对 httpx 同时测了 h1 与 h2 两种配置。
- **WebSocket**：内置 WebSocket 客户端且实测可用的：aiohttp、curl_cffi、nb_curl。其余需要额外的第三方 WebSocket 库。
- **压缩解码**：对 gzip / deflate / br / zstd 四种 Content-Encoding 的自动解码覆盖情况见上表。

## 4. 请求指纹评分

评分来自第三方公共检测站 [https://www.xcctls.top/score](https://www.xcctls.top/score)：以最新版 Chrome 为基线，从 TLS ClientHello、HTTP/2 帧到请求头逐项比对并扣分，满分 100，分数越高越接近真实浏览器。每一条都先用该库自己的配置建立连接，再用**同一个库、同一套配置**读取属于那条连接的评分结果。

![4 请求指纹评分（xcctls 满分 100）](charts/4-fingerprint-score.svg)

## 5. HTTP/3

本轮不单独评测各库的 HTTP/3 实现。要确认某个客户端是否**真的走了 QUIC**，直接访问 [https://h3.xcctls.top/h3_data](https://h3.xcctls.top/h3_data)：它会返回这条连接是不是 HTTP/3，并给出连接的详细信息（ALPN、HTTP/3 SETTINGS、QPACK 参数、QUIC ClientHello 解析等）。判定以服务端回报的 ALPN 为准 —— 只看「连得上」不算。

## 6. 公平性与局限

### 我们做了什么来保证公平

- 同一台服务端、同一份负载、同一批 URL，所有库完全相同。
- 每档并发取 3 次重复的中位数，且丢弃预热阶段。
- 逐单元采样服务端 CPU，确认服务端没有成为瓶颈。
- 发现系统代理污染后作废全部相关数据并重跑，而不是打补丁解释。
- 曲线同时给出吞吐与 p50/p95/p99，不用平均值掩盖尾部。

### 本报告做不到的事

- **不是绝对性能排名。**结论只在这套客户端/服务端组合下成立；换硬件、换网络、换服务端实现，绝对值都会变。可信的是相对关系与量级。
- **同步与异步不可直接比大小。**线程池与事件循环是两种不同的资源模型，本报告把它们并列展示，而不是合成一个分数排名。
- **HTTP/3 不在本报告的评测范围内**：怎么自行确认见第 5 节。
- **指纹评分只反映被评分的那些维度。**评分服务覆盖 TLS ClientHello、HTTP/2 帧、请求头构成等，不代表真实风控系统的全部判定逻辑。
- **测试场景有限。**只用到一个服务端、两种响应体大小、无代理链路、无丢包与高延迟。真实公网的长连接、弱网、代理与被封场景未覆盖。

### 一句话结论

如果目标是**拿到与真实 Chrome 一致的网络指纹**，nb-curl 在本次评测里是唯一能把TLS 指纹与 HTTP/2 帧一次性对齐的库（请求头构成与指纹评分见第 4 节），并且支持 HTTP/3（如何自行确认见第 5 节）；代价是吞吐与 CPU 效率低于纯 HTTP 客户端，因为浏览器仿真本身就是额外的计算工作。如果不需要指纹仿真，普通 HTTP 客户端在吞吐上仍有优势 —— 这两件事在这个评测里并不冲突。

指纹评分上，nb-curl 取到 95 分（满分 100），是三个指纹仿真库里最高的。

### 该动手改的东西

本轮实测撞到过两条 **nb-curl 自身**的缺陷 —— F5 同名 Cookie 被发两次、F7 `iter_content()` 只是整体缓冲后的切片。两条都已修复并重测：功能矩阵里 F5 已回到 ✓、F7 的首块时间约 2 ms（整体约 1.0 s），「检查中发现的问题」一节也不再列出它们。<br>下表列的是**实测中仍然存在**的、需要各自作者留意的点。

1. **证书校验**：requests_go 在浏览器 TLS 预设路径下 `verify=True` 不生效，用它做采集时要注意这一点；nb-curl 与 curl_cffi 在这条路径上是正常拦截的。
2. **httpx 的异步客户端**（见第 2 节问题清单）：在 Windows 默认 Proactor 事件循环下，并发 64 以上会出现数量级退化；同一份代码在 Linux 上通常不会这么差。
3. **性能上**：nb-curl 在同步/高并发档位的吞吐与 CPU 效率都排在前列，指纹仿真的开销主要体现为 TLS 握手场景（3.5 节）与逐请求 CPU（3.4 节），这是可接受的代价。
